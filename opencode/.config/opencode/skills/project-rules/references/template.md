# Code style

## Stack

- Language: `<LANGUAGE> <VERSION>`
- Framework: `<FRAMEWORK or none>`
- Package manager: `<PACKAGE_MANAGER>`
- Formatter: `<FORMATTER_COMMAND>`
- Linter: `<LINTER_COMMAND>`
- Type checker: `<TYPE_CHECKER_COMMAND or none>`
- Tests: `<TEST_COMMAND>`

## Code style

- Functions: 4 to 20 lines. Split if longer.
- Files: under 500 lines. Split by responsibility.
- One thing per function, one responsibility per module (SRP).
- Names: specific and unique. Avoid `data`, `handler`, `Manager`.
  Prefer names that return fewer than 5 grep hits in the codebase.
- Types: explicit. No `any`, no `Dict`, no untyped functions.
- No code duplication. Extract shared logic into a function or module.
- Early returns over nested `if`s. Two levels of indentation at most.
- Exception messages must include the offending value and the expected shape.

## Comments

- Keep your own comments. Do not strip them on refactor. They carry
  intent and provenance.
- Write WHY, not WHAT. Skip `// increment counter` above `i++`.
- Docstrings on public functions: intent plus one usage example.
- Reference issue numbers or commit SHAs when a line exists because
  of a specific bug or upstream constraint.

## Tests

- Tests run with a single command: `<TEST_COMMAND>`.
- Every new function gets a test. Bug fixes get a regression test.
- Mock external I/O (API, database, filesystem) with named fake classes,
  not inline stubs.
- Tests must be F.I.R.S.T: fast, independent, repeatable,
  self-validating, timely.

## Dependencies

- Inject dependencies through a constructor or a parameter, not a global or an import.
- Wrap third-party libraries behind a thin interface owned by this project.

## Structure

- Follow the framework convention (`<FRAMEWORK>` or the language default).
- Prefer small focused modules over god files.
- Predictable paths: controller/model/view, src/lib/test, and so on.

## Formatting

- Use the language default formatter: `<FORMATTER_COMMAND>`.
- Do not discuss style beyond the formatter output.

## Logging

- Structured JSON when logging for debugging or observability.
- Plain text only for user-facing CLI output.

## Branches

- Format: `<type>/<issue>-<slug>` when an issue exists, `<type>/<slug>` otherwise.
- Types: feat, fix, refactor, chore, docs, test, perf, ci, build, hotfix.
- Lowercase, kebab-case, max 50 characters, no spaces.
- issue: optional   # optional (default) | required | never
- Branch from an up-to-date base. Rebase onto the base before opening a PR.

## Commits

- Format: `<type>(<scope>): <subject>` (Conventional Commits).
- Types: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.
- Subject: imperative, present tense, capitalized, no period, max 70 characters.
- Body: explain what and why, not how.
- Footer: reference issues (`Fixes #123`, `Refs #123`).
- No AI attribution. Never add `Co-Authored-By`, "Generated by AI", or any AI mention. All changes are the author's own.

## Pull requests

- One PR per feature or fix.
- Title uses the commit format.
- Body: what changed, why, and context for the reviewer. No test-plan section.
- Open as draft by default (`gh pr create --draft`).
- merge: squash   # squash (default) | rebase | merge-commit
- Never merge from this skill.
