# Commit Conventions

Produce one clean commit per logical change, in the project's own convention.

This skill never pushes, never opens a pull request, and never merges.

## Step 1: Read the project convention

Read `CODE_STYLE.md` at the repository root. Use its `Commits` section for the format, the allowed types, and the subject rules.

If the file or the section is absent, use Conventional Commits as the default, described below.

## Step 2: Inspect the change

Run these, from the repository root:

```bash
git status
git diff --staged
git diff
```

Read the intent, not only the files. If the change mixes unrelated subjects, propose a split into separate commits before you continue.

## Step 3: Check the branch

```bash
git branch --show-current
```

If the current branch is `main` or `master`, warn the user and ask before you commit. Do not create or switch a branch on your own.

## Step 4: Draft the message

Format:

```
<type>(<scope>): <subject>

<body>

<footer>
```

The header is required. The scope and the body are optional. Keep every line under 72 characters.

Default types:

| Type | Purpose |
|---|---|
| `feat` | New feature |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `style` | Formatting, no logic change |
| `refactor` | Refactor, no behavior change |
| `perf` | Performance improvement |
| `test` | Tests |
| `build` | Build system or dependencies |
| `ci` | CI configuration |
| `chore` | Maintenance |
| `revert` | Revert a previous commit |

Subject rules:

- Imperative and present tense: "Add feature", not "Added feature".
- Capitalize the first letter.
- No period at the end.
- Maximum 70 characters.

Body: explain what and why, not how. Use the imperative mood.

Footer: reference issues with `Fixes #123` (closes) or `Refs #123` (links). Add the footer only when it carries a real reference.

## Step 5: Show, then commit

Show the full message to the user. After approval, stage the intended files and commit:

```bash
git add <files>
git commit -m "<subject>" -m "<body>"
```

## Guards

- **No AI attribution. Never.** Do not add `Co-Authored-By`, "Generated by", "Written with", or any mention of a tool, model, or assistant. The change is the author's own. When in doubt, omit.
- Never invent an issue number.
- Never commit secrets, credentials, lockfile noise, or unrelated files. Check `git status` before staging.
- Match the repository style. Do not restyle a message the project already writes differently.
- One logical change per commit. Keep the repository working after each commit.
